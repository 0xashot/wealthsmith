# Suggestion Card

Suggestion cards present WealthSmith recommendations generated by the Suggestion Engine.

They help users understand what WealthSmith is suggesting, why it matters, how urgent it is, and what action they can take next.

This component extends the base card contract in `components/card.md`.

---

## Purpose

Use suggestion cards to display structured recommendation outputs from the WealthSmith Suggestion Engine.

A suggestion card should communicate:

- What the suggested action is
- Why the suggestion is relevant
- Whether the suggestion is the Top Pick
- The priority or importance of the suggestion
- The expected user action
- Supporting context from deterministic engine output
- Any relevant caution, requirement, or explanation

Suggestion cards should feel calm, trustworthy, and explainable.

They should not pressure the user.

---

## Important Rule

Suggestion cards display suggestion data.

Suggestion cards do not decide suggestion logic.

The card must not determine:

- Which suggestion appears
- Which suggestion is the Top Pick
- Why the suggestion was triggered
- How safety buffer is calculated
- How portfolio gaps are calculated
- Which token is selected
- Which protocol is selected
- How ranking works
- How risk level affects recommendation logic
- What Smith AI should say

That logic belongs in `rules/` and backend/product logic.

The card should render structured data provided to it.

---

## When to Use

Use a suggestion card when showing a recommendation to the user.

Examples:

- Build safety buffer
- Increase stablecoin allocation
- Reduce concentration risk
- Review under-diversified exposure
- Consider staking idle assets
- Review available yield strategy
- Add wallet or address
- Complete onboarding information
- Learn why a portfolio gap exists

Suggestion cards can appear in:

- Dashboard
- Suggestion feed
- Portfolio review
- Top Pick module
- Smith AI context panel
- Empty or incomplete portfolio states
- Onboarding follow-up states

---

## When Not to Use

Do not use a suggestion card for:

- Static educational content with no action
- Generic dashboard cards
- Portfolio metrics
- Asset rows
- Protocol comparison tables
- Chat messages
- Marketing claims
- Manual financial advice not generated by the Suggestion Engine

Do not use suggestion cards when the content is not backed by structured suggestion data.

Do not create ad-hoc suggestions in the frontend.

---

## Data Source

Suggestion cards should be rendered from structured suggestion output.

Expected data may include:

```text
id
title
summary
reason
priority
category
status
isTopPick
actionLabel
actionType
supportingMetrics
riskNotes
requirements
dismissible
createdAt
```

The exact schema can evolve, but the component should assume the suggestion comes from deterministic product logic.

The frontend should not invent missing reasons, numbers, rankings, or labels.

When required data is missing, the component should use an approved fallback state instead of guessing.

## Layout

Suggestion cards should be easy to scan.

Recommended structure:

```text
[Top Pick badge] [Category / priority badge]

Title

Short explanation or reason

Supporting metric or evidence, if available

Risk / requirement note, if needed

[Primary action] [Secondary action]
```

Keep the card focused on one suggestion.

Do not combine multiple unrelated suggestions into one card.

## Variants

### Default Suggestion Card

Use for normal recommendations.

Examples:

- Add more stable assets
- Review BONK exposure
- Consider staking idle SOL

Token guidance:

- Background: `color.surface.card`
- Border: `color.border.subtle`
- Radius: `radius.surface.md`
- Shadow: `shadow.card.default`
- Padding: `spacing.card.padding.md`
- Gap: `spacing.card.gap.md`

---

### Top Pick Suggestion Card

Use for the single highest-priority suggestion selected by the deterministic ranking system.

The card may visually stand out, but it should remain calm.

Token guidance:

- Background: `color.surface.card`
- Border: `color.action.primary.background.default` or approved semantic emphasis token
- Radius: `radius.surface.lg`
- Shadow: `shadow.card.selected`
- Badge: `color.feedback.info` or approved Top Pick semantic token
- Padding: `spacing.card.padding.lg`

Top Pick display rules:

- Only one suggestion should be shown as Top Pick in a given suggestion set.
- The card can display the Top Pick badge only when `isTopPick` is true.
- The card must not decide Top Pick itself.
- If multiple cards are marked Top Pick, treat it as a data issue and do not invent resolution logic in the component.

Recommended badge text:

```text
Top Pick
```

Avoid:

```text
Best Investment
Guaranteed Best
Highest Return
Must Do
```

---

### Warning Suggestion Card

Use when the suggestion addresses a risk, missing requirement, or safety concern.

Examples:

- Safety buffer not fully covered
- Portfolio is highly concentrated
- Required onboarding data is missing

Token guidance:

- Status color: `color.feedback.warning`
- Text must explain the issue calmly
- Do not rely on warning color alone

Warning cards should explain what the user can do next.

---

### Info Suggestion Card

Use for educational or lower-urgency suggestions.

Examples:

- Learn why stable assets matter
- Review idle assets
- Connect another wallet for a fuller view

Token guidance:

- Status color: `color.feedback.info`
- Tone should be educational and low-pressure

---

### Success Suggestion Card

Use when a suggestion is completed, resolved, or no longer urgent.

Examples:

- Safety buffer funded
- Wallet connected
- Suggestion completed

Token guidance:

- Status color: `color.feedback.success`
- Show completion state clearly
- Avoid over-celebration or hype

---

### Blocked Suggestion Card

Use when a suggestion cannot be acted on yet.

Examples:

- Wallet not connected
- Required profile field missing
- Safety buffer requirement must be resolved first
- Protocol temporarily unavailable

Blocked cards should explain:

- What is blocking the action
- What the user can do next
- Whether the suggestion is informational only

## States

Suggestion cards may support these states.

### Default

Suggestion is visible and actionable or informational.

### Hover

Use only when the card is interactive.

Use:

- `motion.interaction.hover`
- `shadow.card.hover`

### Focus

Required when the card itself is clickable or contains interactive elements.

Use:

- `shadow.control.focus`
- `color.focus.outline.default`

### Selected

Use only when the user can select a suggestion.

Selection should not mean Top Pick unless the data explicitly says so.

### Loading

Use while suggestion data is loading or being refreshed.

Loading cards may use skeleton states.

Loading states should preserve approximate layout size to reduce layout shift.

### Empty

Use when there are no suggestions to show.

Empty states should explain the situation calmly.

Example:

```text
No suggestions right now.
```

Avoid:

```text
You are all set forever.
```

### Error

Use when suggestions fail to load.

Error states should explain what happened and provide a recovery action.

Example:

```text
We could not load suggestions. Try again.
```

### Dismissed

Use when a user dismisses a suggestion.

Dismissed suggestions should not disappear without clear product intent.

The component can display a dismissed state, but dismissal persistence belongs in product logic.

### Completed

Use when the suggested action has been completed.

Completed cards should be visually calm and clear.

### Correct


## Icons

Suggestion cards may include an icon next to the title.

Icon selection is driven by the structured suggestion data, not by the component's judgment.

### Protocol-tied suggestions

A suggestion is protocol-tied when its structured data includes a protocol
decision with a specific destination (for example
`protocol_decision.destination_protocol_id`), or when its title or primary
action names a specific protocol.

Protocol-tied suggestion cards use the approved protocol icon from
`assets/icons/protocol/`.

Examples:

```text
Deposit USDC into Kamino -> assets/icons/protocol/kamino.svg
Swap BONK to USDC on Jupiter -> assets/icons/protocol/jupiter.svg
Stake SOL on Marinade -> assets/icons/protocol/marinade.svg
```

Rules:

- The protocol icon must be paired with the visible protocol name in the
  card copy or CTA. Icon alone is not identity.
- The icon reflects the protocol destination selected by Protocol Logic.
  The icon never decides or implies protocol selection.
- Preserve approved protocol brand colors. Do not recolor protocol icons.

### Generic suggestions

Generic UI icons from `assets/icons/ui/` are only for generic safety, risk,
wallet, or informational suggestions that have no specific protocol identity.

Examples:

```text
Top Up Your Safety Buffer (no protocol destination) -> assets/icons/ui/shield-check.svg
Why Safety Buffer comes first (informational) -> assets/icons/ui/info.svg
```

### Missing icons

- Do not invent icon paths. Use approved paths from
  `assets/icons/icon-registry.json`.
- Do not use protocol fallback icons in MVP. If a protocol icon is missing
  from the registry, treat it as an implementation issue and report it;
  render the visible protocol name without a broken image or an unapproved
  substitute.

### Accessibility

- Card icons are decorative next to visible text: `aria-hidden="true"`.
- Icons are never the only source of meaning on a suggestion card.

### Protocol Handoff CTA

An external protocol handoff CTA (for example "Review on Jupiter") is a
button-styled link.

Rules:

- It may be implemented as an accessible anchor element for correct
  external-link behavior (opens in a new tab, `rel="noopener noreferrer"`),
  but it must be styled as a WealthSmith button, not an inline text link.
- The label must not use browser-default underlined link styling.
- It carries a trailing external-link icon that stays visible and
  communicates the external destination.
- Enabled state: the label, border, and external-link icon share the CTA's
  primary action color (they inherit the CTA text color; see
  `components/button.md` — Button Icons).
- Disabled, locked, or unavailable CTAs use the disabled foreground color
  for both label and icon.
- Hover, focus, and active states keep the icon color synchronized with the
  label color.
- Use semantic color tokens only; do not hardcode raw icon or text colors.
- Opening the protocol does not execute a transaction, request a wallet
  signature, move funds, or mark the suggestion complete (MVP;
  rules/protocol-selection-rules.md).

## Priority Display

Suggestion cards may display priority if provided by the Suggestion Engine.

Priority display should be calm and descriptive.

Allowed examples:

```text
High priority
Medium priority
Low priority
Action needed
Review when ready
```

Avoid urgency pressure:

```text
Act now
Urgent profit
Do this immediately
Limited time
```

The card must not calculate priority.

## Supporting Metrics

Suggestion cards may display supporting metrics when provided.

Examples:

```text
Safety buffer covered: 27%
Target buffer: $3,000
Current stable assets: $800
SOL exposure: 73%
Estimated APY: 6.2%
```

Rules:

- Use exact values from structured data.
- Do not invent numbers.
- Do not round in a way that changes meaning.
- Do not hide important assumptions.
- Use `typography.metric.compact` or `typography.metric.secondary` for numeric values.
- Use `typography.body.sm` for metric labels.

When values are unavailable, show an approved fallback or omit the metric.

Do not guess.

## Actions

Suggestion cards may include:

- Primary action
- Secondary action
- Dismiss action
- Smith AI explanation action

Examples:

```text
Review suggestion
View details
Learn why
Connect wallet
Add stable assets
Dismiss
```

Use `components/button.md` for button behavior.

Primary action rules:

- Use one primary action per card.
- The action should match the suggestion intent.
- The action label should be specific.
- Do not use action labels that imply execution unless the product supports execution.

Avoid:

```text
Invest now
Buy now
Maximize gains
Get rich
Guarantee yield
```

Prefer:

```text
Review suggestion
View details
Learn why
Connect wallet
Add wallet
```

## Smith AI Trigger

Suggestion cards may include a Smith AI explanation trigger.

Examples:

```text
Ask Smith AI
Explain this
Why this suggestion?
```

The trigger opens or focuses Smith AI with the suggestion context.

The card should pass structured suggestion context to Smith AI.

The card should not generate Smith AI's explanation itself.

Smith AI should explain existing deterministic logic; it should not invent financial logic.

---

## Dismiss Behavior

Suggestion cards may include a dismiss action when allowed by product logic.

Dismiss action examples:

```text
Dismiss
Not now
Hide
```

Rules:

- Dismiss must not be the primary action.
- Dismiss should be visually low-emphasis.
- Dismiss should not remove critical safety warnings unless product logic allows it.
- Persistence of dismissed state belongs in product logic, not the component.

---

## Responsive Behavior

Suggestion cards should be mobile-first.

### Mobile

- Cards should stack vertically.
- Use compact but readable spacing.
- Actions may stack vertically.
- Avoid dense metric grids.
- Keep explanations short.
- Top Pick badge should remain visible without crowding the title.

### Tablet

- Cards may appear in one or two columns.
- Keep related suggestion groups aligned.
- Avoid overly long card widths.

### Desktop

- Cards may appear in dashboard grids or suggestion feeds.
- Featured Top Pick cards may span more columns.
- Supporting metrics can be displayed inline when readable.

### Wide

- Keep card content within readable widths.
- Do not stretch explanation text too wide.
- Use grid structure for multiple suggestions.

---

## Accessibility

Suggestion cards must support accessibility by default.

Requirements:

- Use logical heading structure.
- Ensure badges and status indicators have readable text.
- Do not rely on color alone.
- Ensure interactive cards have visible focus.
- Make buttons keyboard accessible.
- Use accessible names for icon-only controls.
- Communicate loading and error states clearly.
- Keep contrast WCAG AA compliant.
- Respect reduced motion settings.

If the entire card is clickable:

- Use correct link or button semantics.
- Do not nest conflicting interactive targets.
- Ensure the action is clear to screen readers.

Status examples should be available as text:

```text
Top Pick
High priority
Completed
Action needed
```

## Content Rules

Suggestion card copy should follow WealthSmith voice:

- Clear
- Calm
- Trustworthy
- Beginner-friendly
- Specific
- Non-hype
- Explainable

Titles should be short and action-oriented.

Good title examples:

```text
Build your safety buffer
Review your BONK exposure
Consider staking idle SOL
Add another wallet
Increase stable assets
```

Avoid vague titles:

```text
Important update
Portfolio thing
Action required
Opportunity
Best move
```

Summary text should explain the reason in plain language.

Good summary example:

```text
Your stable assets do not fully cover your target safety buffer yet.
```

Avoid:

```text
You must fix this now to avoid missing out.
```

Do not invent financial claims, projected returns, or risk-free language.

Avoid:

```text
Guaranteed return
Risk-free yield
Best investment
Maximize profits
```

## Do

- Use this component for structured WealthSmith suggestions.
- Build on top of `components/card.md`.
- Use semantic tokens.
- Display Top Pick only when provided by data.
- Keep one suggestion per card.
- Keep copy clear and calm.
- Show supporting metrics only when provided.
- Use badges carefully.
- Use accessible text for status and priority.
- Keep business logic outside the component.

---

## Do Not

- Do not calculate suggestion priority in the card.
- Do not determine Top Pick in the card.
- Do not invent missing reasons or metrics.
- Do not hardcode raw visual values.
- Do not use hype-based financial copy.
- Do not imply guaranteed returns.
- Do not rely on color alone for status.
- Do not put protocol selection logic inside the component.
- Do not generate Smith AI explanations inside the card.
- Do not use this component for generic content that is not a suggestion.
